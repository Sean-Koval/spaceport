# Domo named-query gateway pilot

15 October 2026. Implementation-ready design candidate for the consolidated pilot review; no implementation or live activity is authorized by this file. Repository inspected: `/workspace/shared/spaceport-connectors-integration`, HEAD `fe6055f`.

## 1. Outcome and boundaries

Implement a real configured Domo serving path through the existing gateway author → isolated test → publish → execute → retrieve lifecycle. Use direct documented SQL query HTTP, not a fabricated Cube driver or an assumed MCP SQL tool. Preserve the four public MCP tools, ordinary REST schemas, current publisher workflow, legacy Cube behavior, and existing offline `domo-named-v1` contracts.

The new revision is `domo-named-v2`. It supports a finite operator-reviewed statement catalog selected by the entire normalized request and exact server-derived authorization scope. It has no SQL interpolation, generic compiler, unrestricted dataset explorer, source writes, implicit connection setup, or automatic retries.

An explicit operator-owned source descriptor authorizes configured serving. Installing it is a trust/configuration action, not evidence of measured compatibility. There is no `verified=true` flag, privileged qualification route, new activation state machine, or unpublished-product bypass. A first explicit source check is an ordinary bounded query against a published version, or an already-approved isolated fixture execution. Evidence is recorded afterward and identifies exactly what ran. No configuration can claim unsupported PDP delegation, source scan limits, cancellation, or freshness.

Implementation and offline/backend-fixture verification may proceed after consolidated spec/plan approval. Creating credentials, OAuth grants, IAM, resources, real queries, source changes, publication to an external deployment, and deployment itself remain separately authorized operator actions.

## 2. Primary-source facts and selected wire profile

### Query

The official [DataSet API YAML](https://github.com/DomoApps/domo-documentation-hub/blob/main/portal/API-Reference/Domo-APIs/DataSet-API.yaml) and [query documentation](https://www.domo.com/docs/portal/52fd0777839f4-query-a-data-set) describe `POST https://api.domo.com/v1/datasets/query/execute/{dataset_id}`, bearer authentication, and a JSON body with `sql`. The successful response example contains `datasource`, `columns`, `metadata`, `rows`, `numRows`, `numColumns`, and `fromcache`. Metadata examples use `STRING`, `DOUBLE`, `LONG`, and `DATETIME`, with `dataSourceId`, `maxLength`, `minLength`, and `periodIndex`. The schema's string-item declaration for `rows` conflicts with its positional-array examples. This implementation deliberately supports the example's array form, not both interpretations.

Name the selected internal profile `domo-query-positional-v1`. It is a documented-example compatibility profile, not a claim that every tenant response has been observed.

The protocol-success parser requires:

- HTTP 200 received from the exact HTTPS request, with no redirect; MIME `application/json`, absent/UTF-8 charset only; absent/identity content encoding; no transformed/decompressed body.
- A completely received bounded raw byte stream, valid UTF-8 JSON, no duplicate keys, no nonfinite numbers, no nested row values, and exactly the seven named top-level keys.
- `datasource` equals the pinned dataset UUID; unique string `columns`, each 1–256 characters; 1–50 total wire columns, including any hidden checkpoint; positional metadata and row widths agree; exact integer counts agree with the complete arrays. Booleans are not integers. A checkpoint-enabled binding therefore permits at most 49 public columns; it cannot add an unbounded hidden column outside the wire cap.
- Metadata has required `type` and exact `dataSourceId`, plus only optional `maxLength`, `minLength`, `periodIndex`. Lengths, when present, are strict integers from -1 through 2^31-1; period index is a strict integer from 0 through 2^31-1. Missing optional fields are accepted, explicit null and unknown fields are not.
- Recognized protocol type names are exactly the four documented example names. Cells are bounded JSON scalars, with metadata-corresponding primitive kinds; null is retained as null for subsequent declared-nullability validation. Unsupported types, stringified rows, object rows, extra envelope variants, missing columns, and alternate success/error wrappers fail closed. New observed forms require an explicitly reviewed new profile.

The protocol parser and product parser are separate. A complete success envelope matching exact request/dataset identity can establish synchronous request completion even if the product later rejects changed column names, unsupported product types, unexpected nulls, out-of-range values, or stale freshness. This is the selected documented synchronous-response contract, subject to later actual-provider qualification; it is not a general cancellation/lifetime guarantee for other provider work. A malformed, partial, oversized, ambiguous, wrong-dataset, or unrecognized envelope cannot establish that completion. HTTP 401/403/429/5xx are not assumed to prove that no query ran.

### OAuth

The [official Python transport](https://github.com/domoinc/domo-python-sdk/blob/master/pydomo/Transport.py) uses POST `/oauth/token`, HTTP Basic client credentials, and form fields `grant_type=client_credentials` and `scope`. The [authentication page](https://www.domo.com/docs/portal/1845fc11bbe5d-api-authentication) supplies the HTTPS API origin and a token example containing `access_token`, `customer`, `expires_in`, `jti`, `role`, `scope`, `token_type`, and `userId`. Choose the SDK's POST/form flow; do not switch methods automatically.

The initial token profile requires a bounded string access token, positive integer `expires_in`, `token_type` equal to bearer ignoring case, exact expected `customer` and integer `userId`, and a scope set exactly equal to the requested `data`. Optional `jti` and `role` are bounded known metadata; role may be additionally pinned by operator configuration. Unknown fields and missing identity fields fail closed until a different profile is reviewed. No local JWT decoding creates authority.

The [credential FAQ](https://www.domo.com/docs/s/article/360042934494) describes role/shared-content reach and PDP restrictions generally. It does not establish this query endpoint's employee-level PDP delegation. `data` is not a read-only scope. Runtime method restriction and least-privileged source setup are independent controls.

## 3. Concrete first product and exact values

The first sample is `weekly-account-usage` version `1.0.0`, a daily-grain report over the one reviewed UTC interval `[2026-10-05, 2026-10-12)`. Outputs are `day` DATE, `account` STRING, and `usage_events` DECIMAL(38,0). Grain keys are `(day, account)` and the time field is `day`. The exact supported request/scope pairs are north-all with account absent/null; north-core with account absent/null; north-all with account `acct-a`; and north-core with account `acct-b` (empty result). There are no arbitrary filters or sorts in this catalog. Canonical defaults make equivalent optional-input forms select one deliberate variant; other combinations remain unavailable even if otherwise schema-valid.

North scopes include all of `core,special`, or `core` only. The source returns core `acct-a` values 120 and 180 on October 5 and 6, and special `acct-b` value 50 on October 5. South's `acct-a` value 900 must never appear for north. A south principal is rejected for this north-pinned product before credentials or source I/O. Another tenant needs its own reviewed binding/package; no broadened tenant input is introduced.

The selected sample binding uses source `STRING` for day/account and explicit source `LONG` → gateway decimal(scale=0) for usage_events. Parse raw JSON bytes directly in Python without a JavaScript or binary-float intermediary. Accept only a JSON integer token in signed int64 range; reject bool, float/exponent token, DOUBLE metadata, fractional value, and overflow. Format the exact integer to a decimal string and validate the manifest's precision. A separate explicit STRING → exact-decimal rule can support larger approved values. Existing v1 conversion remains unchanged. No unverified Domo CAST syntax is required or asserted.

The sample statements are retained exact SELECT bytes against the documented `table` relation with fixed scope/date/account predicates, explicit projection, stable ordering and a sentinel row limit. Their actual dialect compatibility and metadata are reported as unverified until an authorized source query succeeds. Prefer a preaggregated daily source whose rows retain tenant/group boundaries and do not mix unauthorized contributions; if aggregation is required, the operator must review exact SQL enforcing constraints before aggregation. A configured source mapping is not proof of business equivalence.

Reject duplicate `(day, account)` grain, dates outside the accepted interval, undeclared output columns and wrong types. Do not borrow Cube member aliases, grain assumptions, or date coercion.

## 4. Immutable source and binding assets

`DomoConnection` is an operator-owned source descriptor with `provider="domo"`, `source_id`, positive revision, descriptor digest, context, `capacity_pool_id`, fixed API origin, OAuth/query profile identifiers, expected customer/user identity, mounted client-ID/client-secret references, optional approved source role, exact dataset allowlist, and `shared-service-identity` authorization mode. Common package references use exactly `{provider, source_id, revision, descriptor_digest, context}`; an optional provider-specific `connection_id` is not a lookup alias. The descriptor pins a source-policy approval reference describing data owner, approved dataset/columns, gateway tenant/audience, and billing/dispatch policy. That reference is authorization provenance, not a successful-test certificate. Source aliases, binding/descriptor revisions and credential rotation retain the registry's same underlying capacity pool and unresolved holds; a new configuration cannot create fresh capacity to evade them.

Secret references accept only explicitly supported mounted-secret paths or an existing approved resolver. Never put values, token-bearing URLs, arbitrary hosts, headers, paths, certificate overrides, or SDK objects into manifests, registry projections, CLI output, browser storage, or logs. The current demo-only 43-character secret reader is not reused. Expected customer/user ID and client-ID identity prevent silently substituting another source account. API processes receive only fixture-connection credentials; workers receive only consumer-connection credentials.

`DomoRuntimeBinding` pins connection/context, dataset, owner/policy/tenant, adapter revision, definition/statement-bundle identity, ordered source/output column mapping, explicit conversion rules, grain/time/input/scope semantics, and finite query variants. Optional checkpoint configuration pins one hidden column and the producer's coherence contract. Its digest covers all execution-relevant fields. Source URLs and secrets remain in the private connection catalog, not the public binding choice.

Persist only `PreparedDomoQuery` references: accepted-spec digest, binding/dataset/source/definition identity, canonical request/scope digests, selected statement ID/revision/hash, response profile, and effective bounds. The payload contains no source session, worker generation, credential or dispatch authority. Pure preparation precedes session issuance; the immutable `source_preparations` database row links this payload/digest to its exact stable session/owner after creation. SQL is re-resolved from the immutable catalog immediately before source I/O. Preserve legacy Cube `PreparedQuery` JSON shape and database validation.

The Domo scope validator requires exact tenant, current policy revision, server-derived row constraints, complete declared field visibility and unchanged effective limits for the execution. A tighter field/limit scope causes refusal rather than a post-download approximation. Current data authority is checked before credential access, before arming the query, before storing the result, and on every retrieval/replay/cursor operation.

## 5. Ordering, transport and token lifetime

1. Resolve the accepted published product, current grant, exact source binding and immutable statement catalog. Validate the complete normalized request and compute the exact finite plan. An unavailable variant stops before credential lookup or sockets.
2. Obtain a stable shared source-session hold under the common admission budget. This is still a no-query-sent state.
3. Resolve bounded credentials and acquire/reuse a private token before recording query send intent. Token HTTP uses only the selected origin/path, with TLS verification, `trust_env=False`, no redirects/retries and bounded bytes/time. Limit token JSON to 16 KiB, token text to 8 KiB, identity strings to 256 characters. The entire execution deadline includes this work.
4. An optional in-process token cache is keyed by exact connection revision/customer/user/client identity, never gateway user input. Expiry is the earlier of provider expiry minus 30 seconds and five minutes from receipt. Never persist or log it. The first implementation may omit caching. Tokens lacking enough lifetime for the remaining bounded operation are not used. There is no refresh-and-repost after query rejection.
5. Recheck current audited policy, exact plan and dispatch fence, then atomically arm one query intent in the common session ledger. Only the returned single-use send authority may invoke the transport. An inability to commit the intent prevents HTTP. Immediately before dispatch, recheck deadline/current authority; do not claim database revocation and network send are atomic. Only the original still-live sender can attest a definite no-I/O abort before invoking query transport. Reclaim/restart cannot infer no-send from missing response or mint a replacement send right; a crash after intent is unknown-held even if HTTP may not have started.
6. Send exactly one POST containing only `sql` with retained statement bytes; use request-local bearer headers, `Accept-Encoding: identity`, and bounded raw streaming. Query transport has no retries, pagination, alternate endpoint, discovery, or SDK fallback.
7. Observe the full response under total monotonic and wall-clock bounds, at most 120 seconds and stricter effective limits. Raw response and complete normalized envelope are independently limited to 1 MiB; product/policy may be tighter. Product row maximum is 1,000. Protocol parsing permits exactly one overflow sentinel beyond the stricter effective product row cap, hence at most 1,001 rows; this only establishes a complete-too-large response and is never returned as truncated success. A response larger than that protocol cap is incompatible and does not supply terminal proof.
8. Parse exact protocol completion, append terminal observation through its narrow observation authority, then validate product output/freshness and reauthorize before transactional result storage. Token failures before arming can settle no-query-sent. Query HTTP failures, disconnects, ambiguous parses and timeouts cannot.

Any normal close fits the total execution deadline. Cleanup/terminal-observation database writes have a separate short bound and never release rows or start source requests. A closed/cancelled socket provides no promise of later observation.

## 6. Shared source-session integration

The common BQ/Domo ledger is the sole owner of admission, dispatch count, persistent holds, terminal observations and release. No adapter-local boolean or timeout is release authority. Its implementation owns PostgreSQL models, migration/privileges, queue transitions and concurrency accounting; Domo only supplies a typed exact plan and source-specific observation. The shared schema is `source_operation_groups` (one capacity hold and aggregate budget per consumer execution or durable fixture test-run invocation created before cases), `source_sessions` (one exact query/scope/case), and provider records `bigquery_source_jobs` or `domo_source_sends`. The physical Domo capacity key is provider plus the exact approved customer/organization identity; source IDs, datasets, credential owners and revisions do not create independent capacity. These limits cover work coordinated by this registry, not other clients querying the organization.

Gateway service APIs are `source_attempt(claim, prepared, current_decision) -> SourceAttemptContext`, `seal_source(context, reason) -> SourceStatus`, `source_status(session_id) -> SourceStatus`, and existing `complete(claim, completed)` with a durable-source-settlement prerequisite on new source paths. `SourceAttemptContext` is frozen and issued only after current authorization/audit and source-session/lease commits. It is separate from every public request and prepared payload.

The Domo provider-store API is `checkAttempt(context)`, `armSend(context, plan_fingerprint) -> DomoSendPermit`, `observeSuccess(permit, observation)`, `observeNotSent(original_live_unused_permit)`, `sealSession(context, reason)`, and `settleGroup(group_id)`. Names are aligned with the shared `PgAdmissionStore` operation family; these are internal methods, not HTTP routes. `domo_source_sends` has a unique session ID, immutable source/dataset/statement/plan/API/profile digests, intent timestamp and private sender-nonce hash. Observation states distinguish intent, exact successful completion and proven-not-sent; no generic caller-controlled `source_complete` boolean exists. The shared ledger owner implements these records/functions in migration `0005_source_lifecycle.py`.

The arm operation is single-use and consumes the persistent dispatch budget without refunds for unknown outcomes. Consumer session uniqueness is its logical owner `(owner_kind, owner_id)`; fixture-case uniqueness is its run/group and fixed case identity. Source/context are immutable columns, not part of a uniqueness key that could be changed to obtain a second session. Neither source aliases nor worker generations produce a second query for the same logical execution. Reclaim cannot re-arm a Domo query. A Domo session is sealed against additional admissions once its sole send intent is committed; the original permit can finish that already-admitted request under current authority. Every predetermined fixture case is sealed or proven-not-sent on completion/abort. Per-case fixture completion requires that case's sealed/terminal session, not whole-group settlement; otherwise sequential cases would deadlock. Group settlement derives that all child sessions are sealed and every intent is independently terminal/proven-not-sent. The whole fixture source group has an absolute deadline no longer than 120 seconds; each case clamps its own product/policy deadline to that group deadline.

`domo_source_runtime` is a separate narrow database privilege role for the trusted Domo transport/store path, with distinct consumer/fixture login-role context restrictions. Functions enforce the exact `session_user` mapping to provider/context/source-profile authority. The gateway application role cannot write terminal observations or directly release holds. Source runtime methods are limited to exact configured source/context sessions and cannot alter policies, results, source mappings, budgets or ownership. Source-role connection credentials are private process mounts, separate from the ordinary registry app role. Runtime composition receives a second role-limited connection for the adapter; API uses fixture scope and worker uses consumer scope. The same Python process owns both connections, so this is role/typed-interface protection against prohibited operations, not compromise-proof process isolation. The reviewed adapter and authenticated TLS response parsing remain trusted components; the database cannot authenticate a remote response itself. Migration 0005 creates PUBLIC-revoked schema/functions and remains compatible with the legacy four-role test topology. Explicit source-pilot provisioning separately validates existing provider roles and grants their narrow functions; it does not silently create source logins or credentials.

Adapter dispatch is a finite trusted `AdapterRegistry`, selected only from retained binding revision/source descriptor. Registration defines `requires_source_context` and provider kind; no manifest boolean or client input controls these. `prepare(...)` returns legacy Cube preparation or `PreparedDomoQuery`; `source_plan(spec, prepared, executed_decision)` supplies immutable identity/bounds to the common queue. `execute_step(prepared, current_decision, source_attempt, spec, executed_decision, ...)` returns a bounded candidate or Pending. Legacy registrations wrap existing `poll`; BQ can return Pending, while Domo never returns Pending and refuses an already-armed session without provider I/O. Worker/FixtureRunner own the shared gate → context → execute-step → seal/status → current-result-gate → complete flow. Candidate completion never settles a source hold. The same registration dispatches binding/scope checks, fixture equivalence, normalization and stored-result validation.

Observation authority is distinct from the dispatch lease. The trusted dispatch path receives an internal capability bound to the exact armed intent and source plan. It permits only idempotent completion evidence and settlement of that session, including after lease expiry, policy revocation or execution deadline. It cannot send, admit new work, expand a budget or publish rows. A process crash before durable evidence leaves the hold unknown even if Domo might have finished.

Terminal observation records profile, session/intent/plan identity, source connection/dataset, response SHA-256, successful-envelope shape/count identity, and actual observation time. It contains no SQL, credentials, raw errors or rows. Product/schema/freshness failure after valid terminal proof withholds rows but does not falsely imply the synchronous request is still running. A crash after proof but before result persistence fails the result safely and never repeats the source request.

Local timeout, lease expiry, changed policy, application terminal state and a client closing a connection do not release unknown source capacity. Unknown holds are visible to a private operator diagnostic and require exact-attempt independently justified recovery; the pilot adds no automatic manual-reset command masquerading as completion. Legacy Cube reservations retain their existing rules.

The single consumer execution has a one-send cap. The sample fixture run has the four positive fixed cases enumerated in section 3, including the empty north-core/account=`acct-b` result; permission and input-negative cases must send zero queries. The fixture run's durable aggregate group has a four-send ceiling in addition to each case's one-send ceiling and the deployment/source dispatch budget. Retries, reclaims or new attempts inside that run cannot multiply the ceiling. Fixture data scope belongs to the approved fixed fixture principal, while admission/budget ownership belongs to the requesting author, consistent with existing capacity accounting. A deliberate later test run is a separately authorized run, still charged against the persistent deployment/source budget. This does not establish a provider scan or dollar ceiling.

## 7. Business semantics, identity and freshness

The initial supported policy is explicitly shared-service identity. The approved dataset/columns may be disclosed only to the approved gateway scopes, independently of what the source credential can read. Mandatory tenant/group restrictions apply before aggregation. Do not claim each employee's Domo permissions are being delegated. Per-employee PDP preservation remains unavailable until independently verified; no flag enables it.

The operator retains authoritative card/Beast Mode/SQL definitions, schema and immutable query revisions, including date/grain/null/decimal/scope semantics and reviewed change control. Every query verifies its pinned catalog and actual response contract. A hash of an old card does not prove the current card is unchanged. If continuing card equivalence requires source-definition observation that is absent, describe the product as the explicitly approved retained SQL definition instead of claiming ongoing live-card equivalence. Unsupported semantics fail closed; automatic formula extraction/compilation is outside this pilot.

For the first sample, freshness is explicitly optional and is returned as unknown unless valid configured source evidence exists. There is no manufactured fresh timestamp. A freshness-required product is eligible only with a reviewed producer-coherence contract and one exact hidden checkpoint returned with the rows, tied to the plan and response digest. The source must publish the checkpoint and scoped rows coherently; column naming alone is no proof. Reject missing/mixed/future/stale checkpoints. Empty results remain unknown unless the selected response contract genuinely supplies coherent empty-result evidence. Independent dataset metadata and `fromcache` cannot freshen the returned result.

Current policy is rechecked after the read and on every stored-result access. Cache status cannot substitute for authorization. Retained results use the existing principal-isolated, audited, bounded storage and expiry rules.

## 8. Authoring, tests, publishing and readiness

The source/package loader makes operator-approved bindings available through the existing authorized choices. The author selects the sample template/version and can edit presentation metadata, test, review and publish. Execution-contract or version changes without matching finite operator variants are rejected. Source setup is not a publisher form.

Fixture equivalence is adapter-specific. Pin both consumer and fixture connection/context/dataset/definition/catalog/auth-policy identities and an explicit logical-equivalence map. Logical schema, grain, time, input and scope semantics must match; allowed deployment/statement differences are enumerated rather than ignored wholesale. Fixed fixture principal scopes have their own exact variants. The fixture credentials/dataset are isolated from consumer credentials/dataset, and the fixture transport cannot be selected for a live consumer binding.

Fixture proof and published product pins retain the exact draft, consumer/fixture bindings, policy revision, fixture catalog, source-policy configuration and recorded transport mode. Synthetic fixture success is reported as synthetic; it cannot become a statement that the live source was tested. Existing immutable publication and author/publisher/data-role separation remain authoritative.

There is no inactive-publication activation protocol. Operator-configured consumer serving is available through ordinary published-product execution, with all source/session/current-policy checks. An explicit CLI source check uses this same path, not a privileged verifier. Its outcome may provide exact-source evidence without changing the authorization model.

Readiness does not execute a query or obtain a consumer token from the API process. It checks registry migration/access, current configured identities/policy, local immutable assets and compatible source-session/adapter contracts. Distinguish process/configuration readiness from observed live-source compatibility in diagnostics and documentation.

## 10. Acceptance and honest evidence

1. A real application-service test uses disposable PostgreSQL and the existing author save → fixture test → publish → consumer submit → worker → get-result lifecycle. Only external Domo HTTP is faked. Assert audit, immutable evidence, source-session hold and result rows, not merely helper outputs.
2. REST and the existing four MCP tools produce equivalent decisions/results. Public schema snapshots remain unchanged unless an independently reviewed unavoidable change is identified before implementation.
3. Token acquisition cannot occur for an unknown variant or denied scope. Pin customer/user/client identity and requested scope; test expiry, malformed/oversized token responses, unavailable secrets, no logs, and no refresh/repost after query 401.
4. Test exact supported success envelopes and every rejected variant; strict metadata bounds; raw byte limits; no redirects, decompression or extra request; malformed/partial/error/unknown outcomes retain holds. Valid protocol success followed by product rejection can settle source without rows.
5. LONG decimal0 cases include signed int64 boundaries and values beyond JavaScript's exact integer range; reject exponent/fraction/bool/DOUBLE/overflow. STRING decimal tests preserve declared precision/scale without rounding. Null, empty, column order/count, duplicate grain, date bounds and source identity drift fail as specified.
6. Crash tests cover before/after preparation, token acquisition, intent commit, network submission, full response, terminal-proof persistence and result storage. Concurrent/reclaimed workers produce at most one Domo query POST per session. Late proof can settle only the exact source intent, never rows. Unknowns consume capacity after restart.
7. Test current-policy revocation during token acquisition, stream read, completion, stored-result replay and cursor access; tenant/group/visible-field/limit changes release no data. North/core/all/south and reversed cache order are covered.
8. Fixture group caps bound the complete four-case run; negative cases send zero; one case cannot replace its session to obtain extra sends. Fixture/source-policy changes invalidate retained publication evidence. Fake transport/configuration cannot be selected by a live connection.
9. Required unknown/stale freshness fails; optional unknown returns an explicit warning. Independent metadata, `fromcache`, query time and HTTP Date never create source-load evidence.
10. Run complete existing backend-free tests, new disposable-PostgreSQL integration tests, migration privileges/rollback checks, API/MCP snapshot checks and applicable frontend workflow tests. Report passed, failed and not-run separately. No successful fixture or HTTP mock is live-Domo verification.

Remaining live operator inputs are the actual organization and dataset identities, approved credential owner, shared-data audience, immutable named queries, source semantics/change control, optional/required freshness decision, billing/quota and dispatch allowance, and explicit authorization to make the first real query. These do not prevent shipping the complete configured and fixture-tested runtime.
