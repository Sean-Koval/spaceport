# Helix Foundry: concrete reuse assessment

Research date: 13 October 2026. Read-only inspection of official repository metadata, pinned source, licenses, API documentation and test definitions. No Helix software was installed or executed. This is an engineering assessment, not independent performance/security certification or legal advice.

## Decision

**Use Helix Foundry as a selective source and product reference. Keep the approved Python gateway, PostgreSQL registry and Cube execution boundary.** The most valuable immediate transfers are evidence-first publishing review, clear definition diffs, explicit stale-input warnings and permission-filtered provenance. These fit work already approved. Importing its entire workspace, ingestion, ontology storage or AI analyst would create a different product.

The project the user named is [HelixDB/helix-foundry](https://github.com/HelixDB/helix-foundry), not any of the earlier candidates in [foundry-references.md](foundry-references.md). This identification supersedes that document's candidate ambiguity, not its general guidance about licensing and gateway boundaries. The similarly named helixfoundry.ai site is not the repository assessed here.

## 1. License and enterprise boundary

- Foundry's actual [root LICENSE](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/LICENSE) is Apache-2.0. Its [NOTICE](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/NOTICE) attributes HelixDB. The root package and both [SDK](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/packages/sdk/package.json) and [shared package](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/packages/shared/package.json) currently also declare Apache-2.0. Earlier indexed MIT package metadata is stale.
- Selective copying is a viable candidate, subject to preserving the Apache license, applicable notices and attribution, marking modifications, and checking the copied file's dependency tree. This assessment selects no original-code license for our gateway and authorizes no distribution.
- Assets have exceptions: [connector logos](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/apps/web/public/connectors/LICENSE) carry an MIT notice for konpa and [provider logos](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/apps/web/public/providers/LICENSE) an MIT notice for LobeHub. A code license does not confer trademark rights or an endorsement. Prefer our own branding and avoid copying logo collections.
- **No separate proprietary enterprise directory/license was found in the inspected Foundry tree.** That is a scoped source observation, not a claim that every service or dependency in the Helix ecosystem is open source.
- HelixDB is a separate project. At [`16b7a8374f7a97684472a3a1462aa8adaca55e79`](https://github.com/HelixDB/helix-db/tree/16b7a8374f7a97684472a3a1462aa8adaca55e79), its [root license](https://github.com/HelixDB/helix-db/blob/16b7a8374f7a97684472a3a1462aa8adaca55e79/LICENSE) and checked Python/TypeScript SDK licenses are Apache-2.0. No first-party enterprise-license override appeared among license files in that tree. An older [maintainer discussion](https://github.com/HelixDB/helix-db/discussions/783) described HA, managed/self-hosted enterprise operations and RBAC as enterprise-only in February. Treat it as historical, not today's licensing authority. Current [Cloud connection documentation](https://github.com/HelixDB/helix-db/blob/16b7a8374f7a97684472a3a1462aa8adaca55e79/docs/database/helix-cloud/start-here/working-with-enterprise.mdx) describes managed routing and authentication; it does not establish that the whole control plane is included in Foundry.
- Foundry's [Compose file](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/compose.yaml) pins HelixDB image `v0.0.12` by digest. Reading current source licenses does not establish the full provenance/SBOM of that binary image, Ollama, the downloaded model, or transitive packages. Review the actual shipped artifacts before adopting the full stack. No dependency inventory was installed/generated in this pass.

### Security distinction that prevents wholesale adoption

Foundry deliberately assumes one person controls the local computer. In [app.ts](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/apps/api/src/app.ts), a missing Authorization header obtains the local owner's identity. An invalid supplied token is rejected; tokens can be workspace-scoped/read-only. Those are useful local-tool controls, but not the verified multi-user boundary required here. Its [operations guide](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/docs/OPERATIONS.md) warns against network/reverse-proxy/tunnel exposure.

The [data query route](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/apps/api/src/routes/data.ts) accepts dataset IDs and SQL. Our public contract expressly rejects arbitrary SQL and source identifiers. Its [dataset privacy logic](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/apps/api/src/dataset-privacy.ts) controls AI sample sensitivity, not our principal-based row authorization. Do not map “read-only token,” local ownership, or AI masking to equivalent gateway access policy.

## 3. Feature mapping and bounded implementation sequence

These are engineering recommendations. The approved spec/plan remains authoritative, and this document changes neither contracts nor implementation scope.

### A. Implement now within approved V1

1. **Evidence-first review.** Tasks 9/12: show failed checks first, expected/actual values, tested manifest/binding digests and policy revision; label stale evidence with its exact cause. Disable publishing after edits, then enforce the same invariant server-side. Files: `gateway/publishing/{service,test_runner}.py`, `publisher/src/pages/Review.tsx`. Tests: draft edit, binding change, policy change and publication race all require retesting or conflict.
2. **Readable definition diffs.** Tasks 9/12: show added/changed/removed manifest fields, current/proposed values and stable ordering. Use our existing canonicalization, not a new JSON/hash standard. No estimated downstream record impact. Tests: no-op key reordering, meaningful ordered-array change, deleted field, hidden metadata, stale review.
3. **Provenance on product/result detail.** Tasks 8/10/12: present only authorized IDs/digests, tested version, execution time and separately labelled source watermark/freshness. Existing fields suffice; no new graph database. Tests: unauthorized binding/source information remains absent, unknown freshness is not a green badge, pinned version survives current-pointer changes.
4. **Honest status and capability presentation.** Tasks 6/12/13: display existing adapter capabilities and explicit unavailable/mock-tested/live-tested states. A configured BigQuery profile is not a successful live connection. Domo remains unavailable. Tests: unavailable capability cannot be selected; mocked evidence cannot appear as live success.
5. **Contract-driven UI/client behavior.** Tasks 10–12: keep OpenAPI-derived types, reject unknown arguments and preserve REST/MCP parity. An SDK button or UI visibility rule is never the authorization decision.

These improvements can ship alongside the planned publisher rather than waiting for ontology ingestion research. Existing gate tests remain mandatory; do not broaden contracts implicitly to make an upstream component fit.

### B. Small bounded extensions: propose and approve a narrow contract first

| Candidate | Minimum boundary and acceptance criteria | Why not silently fold it in |
| --- | --- | --- |
| Product history panel | Read-only, paginated authorized product versions and lifecycle reasons; no row history or source rewind; tests for hidden versions and withdrawn results. | UI plan has a current diff, but a new history endpoint/permission surface needs a coordinated API contract. |
| Schema-diff impact labels | Compare approved input/output contracts and flag removed/type-changed fields; explicitly describe structural compatibility, not guaranteed business equivalence. | New compatibility rules require agreed semantics and test cases. |
| Read-only dependency map | Render existing product/binding/test/execution references; bound node count and filter every node/edge before counting or rendering. | Even metadata graphs can disclose restricted assets. Start with a list before adding graph dependencies. |
| Metadata export/import into a draft | Export allowlisted non-secret definitions; strict versioned input; map to an approved binding/policy; imported content never publishes itself. | Adds file/serialization and policy-attachment attack surfaces. Helix's export bundle contains constructs our manifests intentionally reject. |

Prefer the first two after the V1 vertical slice is working. They offer visible value without bringing in a graph database or another execution engine.

### C. Architecture expansions requiring a separate proposal

- Ingestion/connectors, CDC, snapshot storage, schema acceptance and scheduled refreshes.
- Operational ontology, cross-source entity resolution, object edits/actions and relationship traversal.
- AI-generated pipelines, free-form SQL, dashboards, conversational analyst or local-model runtime.
- Replacing Cube with DuckDB or HelixDB, or adding a second engine for cross-product joins.
- Multi-user hosting of Helix Foundry, shared-instance API delegation, production tenant controls or managed Cloud features.

Each would need a user problem, data ownership/retention decision, auth model, runtime budget, license inventory and independently tested failure modes. More parallel developers do not remove these dependency and security boundaries.

## 5. API/service-boundary option

If a later requirement is to consume an existing Helix workspace, prefer a narrow adapter or allowlisted export over a fork:

1. Keep gateway identity, authorization, named products, approved bindings, limits, audit and result normalization authoritative.
2. Pin the Helix instance/API version and permit only reviewed resources/operations. Keep its SQL/query, token creation, source configuration, AI and action endpoints away from public MCP/UI.
3. Retain its documented loopback-only trust boundary. Do not put the current app behind a shared reverse proxy as an integration shortcut. A distributed/multi-user deployment needs separate hardening and approval.
4. Require explicit principal-to-data-scope mapping and pre-aggregation row enforcement. A workspace read-only token alone does not prove equivalence to our product policies.
5. Add compatibility, revocation, stale snapshot, pagination, limits, outage and provenance tests before enabling any product. Never claim Helix lineage or freshness as stronger than the observed source evidence.

A safe first experiment is authorized metadata-only export into an unpublished draft. Running live Helix queries through the gateway is a larger source-adapter project, not a small feature import.

## 6. Verification limits and next action

Read actual [comparison tests](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/tests/proposal-comparison.test.ts) and [workflow tests](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/tests/workflow.test.ts): they cover stale input versions, changed generations, workspace separation, schema drift and snapshot citations. These are test definitions, not test results from this environment.

The upstream [validation report](https://github.com/HelixDB/helix-foundry/blob/00d7927d7c08e16c58316e006959f052427e7fa1/docs/VALIDATION.md) is explicit that performance figures are local measurements and that rewritten backup/restore/upgrade scripts had only stub tests at its report date. It also retains older claims that lag current connector code. Do not convert these figures into our scale, memory or production-readiness claims. No Helix runtime, live connector, end-to-end API, UI accessibility, binary provenance or production security test was performed here.

**Recommended handoff:** fold A1–A4 into the existing publishing/UI/adapter owners now, with no new engine or dependency. Finish the authorized V1 acceptance gates. Then choose one bounded extension from B and prepare its small contract change before implementation. Keep C as explicit alternatives, not automatic additions to the current backlog.
