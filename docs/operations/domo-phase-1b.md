# Domo Phase 1b: unavailable until evidence gates pass

15 October 2026. `select_adapter("domo")` still fails with safe `INVALID_INPUT`. The separate `gateway/adapters/domo.py` implements executable **offline contracts with injected transports**, not a live or runtime-registered connector. No Domo SDK, account, credential, native Cube driver, network-client factory or source activation is provided. The default demonstration needs no Domo tenant or paid account.

A live Domo integration remains a **separate read-only adapter for operator-reviewed named queries**, sharing gateway authorization, exact manifest contracts, resource bounds, execution/result isolation and redacted errors. Agent inputs remain typed manifest fields. It must not expose SQL, a credential-bearing SDK, bulk exports, arbitrary card formulas or an unrestricted dataset explorer.


## Implemented offline boundary

`DomoNamedQueryBinding` pins the product binding, owner/policy/tenant, dataset, definition bundle, authoritative-definition digest and ordered output schema. `StatementCatalog` contains immutable operator-reviewed statement bytes and SHA-256 values. A finite `DomoQueryVariant` selects one statement by the **entire normalized request digest and exact server-derived authorization-scope digest**. Statement bytes are copied without interpolation or template substitution. The configured manifest can describe a wider date/filter/sort domain than the finite catalog: an unreviewed combination is still rejected. There is no general dynamic date-range compiler, formula engine, dataset browser or arbitrary SQL tool.

Statements are trusted operator assets, never agent input or publisher-uploaded code. Their digests establish identity, not read-only SQL semantics, PDP equivalence or business correctness. The synthetic fixture statement is not a verified Domo dialect/query. Live execution must independently satisfy every gate below, including pre-aggregation scope enforcement.

`DomoReader` requires an explicitly injected transport and a fresh authorization callback; neither has a default implementation. The callback must supply a current, audited decision for the exact principal and pinned product at `execute` and again at `result`. All result fields must be authorized before submission; changed principal, tenant, policy revision, constraints, visible fields or limits discards the buffered response. Missing/incompatible authority fails closed. No result cache or retained data store is introduced. Injected callbacks and transports receive independent snapshots, and selected statement identity/revision/digest are checked again before source I/O. Raw rows and SQL are omitted from ordinary model representations; explicit serialization still contains data and must not be logged.

One read makes at most one source request with zero automatic retries. Normal response closure occurs inside the same total deadline, before final authorization; error cleanup is separately bounded and cannot release rows. The monotonic deadline covers authorization, selection, reading and validation, capped at 120 seconds and the stricter product/current-policy limit. The response stream has a 1 MiB maximum, the normalized complete result is independently byte-limited, and rows cannot exceed 1,000 or tighter bounds. Reject redirects, non-JSON or transformed responses, duplicate JSON keys, positional column/count/width/type drift and unknown fields. Exact decimals arrive as validated strings; binary floating-point money is never converted into allegedly exact decimals. Zone-less civil timestamps are unsupported.

`DomoFreshnessEvidence` is a trusted internal checkpoint assertion bound to the binding digest, authoritative definition, canonical request, authorization scope and SHA-256 of the exact response bytes. It is not an arbitrary watermark taken from the payload. A future transport must prove that checkpoint and rows are coherent; a later independent dataset metadata read cannot establish this. Missing, changed, future or stale required evidence fails closed. `fromcache` reports only source cache status, never freshness or authorization.

The local readers and the checked-in synthetic fixture are covered by `tests/contract/test_domo.py`, with socket access denied. Successful fake transports prove local validation and no-retry behavior only. They do not demonstrate live API compatibility, provider costs, source completion/cancellation or production authorization. Local timeout is not source termination and cannot release production reservations.

### Explicitly deferred runtime seams

The existing runtime binding resolver, prepared-query persistence, normalization, result replay, publishing checks and readiness remain Cube-oriented. This module is not registered with them and does not return a public `ResultEnvelope`. Safely wiring Domo requires a separately reviewed internal adapter integration plus actual per-product evidence. REST/OpenAPI and the four MCP tools are unchanged. No environment variable, evidence object or profile flag activates Domo.

## Documented API candidates, not compatibility evidence

- Platform OAuth DataSet query: `POST /v1/datasets/query/execute/{dataset_id}` takes a SQL string and documents columns, metadata, positional rows, counts and `fromcache`. This page does not establish prepared binding, end-user PDP delegation, query cancellation or enforced source cost. The eventual named-query adapter must review these properties, map positional columns exactly and reject unsupported behavior. [Official query API](https://www.domo.com/docs/portal/52fd0777839f4-query-a-data-set)
- Platform card definition: `GET /v1/cards/chart/{cardUrn}` exposes chart configuration and calculated fields. It can inform operator reconciliation; retrieving a definition does not demonstrate that a dataset query reproduces it. [Official chart definition](https://www.domo.com/docs/portal/42d54af2095ac-get-chart-card-definition)
- Product Beast Mode endpoints expose expressions and relationships to cards/datasets. That is a different API/credential context; keep this read-only reconciliation work outside agent runtime tools. [Official Beast Mode reference](https://www.domo.com/docs/portal/bff3ab39f7a6b-beast-modes)

Platform OAuth, Product APIs and App-session APIs have distinct identity models. Choose one actual supported tenant/API version and verify its authentication/scopes; never assume a service credential represents the gateway caller or inherits their PDP entitlements. [API families](https://www.domo.com/docs/portal/API-Reference/overview), [Platform authentication](https://www.domo.com/docs/portal/1845fc11bbe5d-api-authentication)

## Per-product activation checklist

Every item remains **UNPROVEN** here. Assign an owner, retain exact reviewed revisions and collect reproducible authorized evidence; configuration and documentation cannot mark a gate passed.

1. **Actual API and licensing/access.** Identify tenant host/ID, supported endpoint/version, scopes, API availability in the authorized subscription, SDK/license if used, and allowed read-only methods. Test credential expiry, renewal, revocation and redacted 401/403/429/outage behavior. Obtain approval before any credentials, accounts, spend or live query. No installation or tenant access is authorized by this document.
2. **Tenant identity and PDP.** Map authenticated gateway principals to verified server-managed tenant/role/entitlement records. Exercise two distinct PDP profiles and same-tenant narrower entitlements, reversed query/cache order, denied metadata and row access, changed PDP while pending, removed access, old cursors and idempotent replay. Observe both rows and discoverability. Do not rely on caller-supplied tenant/user IDs or OAuth token reach as policy evidence.
3. **Service-account and administrator reach.** Determine whose permissions the API actually uses, whether credential owner/admin/bypass roles see more than the caller, and whether PDP is applied to that endpoint. Compare against independent authoritative accounts. If equivalent constraints cannot be independently enforced and demonstrated, that product stays unavailable; no filtering-after-download or bulk-export shortcut.
4. **Authoritative business semantics.** Name each authoritative card, Beast Mode or approved dataset query and retain its exact definition/checksum/revision. Reconcile mandatory and card filters, calculation order, aggregation, grain, nulls, exact decimals/large values, joins, date windows, exclusive end, timezone and DST boundaries. Determine how hidden or unavailable calculated fields affect equivalence. Card metadata is not an executable semantic compiler. Never assume those definitions already exist in BigQuery.
5. **Reviewed query behavior.** Prove safely bound parameters or another explicitly reviewed fixed-query mechanism; reject unsupported filter/sort/types/formulas instead of building arbitrary SQL. Test empty results, null filter semantics, column count/order/type drift and exact result normalization. Unknown/changed definitions fail `BINDING_DRIFT`; backend text stays private.
6. **Time, cost, quotas and rates.** Identify billing and tenant limits, enforceable scan/query/row/byte caps, rate-limit signals/backoff, concurrency and request budgets, source job lifetime/cancellation, and recovery after dropped connections. A row `LIMIT`, client timeout or local retry policy cannot certify source bounds. Keep production disabled until actual enforcement and safe reservation ownership are demonstrated.
7. **Freshness and caches.** Establish what the authoritative load/refresh watermark means for this product; query time is not freshness evidence. Dataset `dataCurrentAt`, `updatedAt` and PDP metadata require product-specific interpretation and tests. `fromcache` alone proves neither caller isolation nor source freshness. Missing evidence remains unknown and required freshness fails closed. [Official dataset metadata](https://www.domo.com/docs/portal/3b1e3a7d5f420-data-set-api)
8. **Drift and ongoing ownership.** Retain immutable manifest/binding/adapter/definition versions, detect changes before execution/release, reconcile known answers after changes, and prove immediate revocation and principal-isolated retention. Record runbooks, operational owner, secrets/egress controls, retention/encryption and restore evidence. No successful synthetic or BigQuery test closes a Domo gate.

## Evidence and dependency policy

Keep authorized Domo evidence separate from mock BigQuery and synthetic PostgreSQL results. Record exact tenant/API and non-secret credential scope, principal/PDP test matrix, authoritative definition revisions, expected/actual reconciliation, drift cases, source bounds, redacted failures and unresolved gaps. No public connector status/schema is invented here.

The existing [integration research](../archive/research/integrations.md) identifies official `pydomo==0.3.0.16` only as a deferred candidate; it has not been installed or compatibility-tested. Any later use needs the exact package/transitive notice inventory and a narrow read-only wrapper, without exposing SDK mutation methods or raw exception text. Original-code licensing and distribution approval remain Task 14 gates.

If tenant identity/PDP equivalence, authoritative business logic or enforceable resource behavior cannot be demonstrated, leave the product unavailable. Documentation is a checklist, not an execution implementation or permission grant.
