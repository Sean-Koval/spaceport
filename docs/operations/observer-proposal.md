# Scoped packet observer: approval and implementation gate

## Current behavior

There is **no approved executable privileged helper, installation, sudo route or packet capture** in this revision. `observer_preflight()` reports BLOCKED without running anything. Demo startup, readiness and business verification remain ordinary unprivileged operations. `verify-demo` runs and retains those actual business results, while its mandatory `offline_egress` slot remains BLOCKED. The aggregate cannot claim complete offline acceptance.

`validate_capture` and `validate_resolver` are source-level admission support, exercised with synthetic fixtures. They are not a capture producer or proof of observed traffic. The approved-observer profile set is deliberately empty; manually supplying a PASS report cannot open it. Existing Docker topology and socket-denial checks provide narrower evidence only. A route declaration or failed socket does not establish packet-level workflow coverage.

## Additional assurance a helper would provide

The missing assurance is application-attributed packet observation across the successful publisher, MCP, REST and optional integration-security workflow, including DNS forwarding. It excludes dependency acquisition and unrelated GitHub runner control traffic. The intended observation points are the eight exact stable container namespaces plus their single inspected bridge, not the whole host.

A reviewed implementation would:

1. Validate the selected private state owner, source/image digests, exact project labels, container IDs/PIDs, namespace identities, bridge/interface membership and absence of other attached networks before and after the window. It must not accept arbitrary namespaces, commands or capture interfaces.
2. Admit a reviewed Docker Engine version **and actual build/GitCommit**, then check bounded effective resolver bytes and explicit `HostConfig.Dns == ['127.0.0.1']` before/after. The candidate platform is Moby/Docker 28.0.4; no runtime build has been admitted here. Its tagged source marks explicit DNS overrides as container-namespace resolvers, unlike host-derived nameservers. Generated metadata must have only `ExtServers: [127.0.0.1]` and `Overrides: [nameservers]`, with internal `nameserver 127.0.0.11`, no host(...) entry, fallback or extra upstream. Unsupported engines or ambiguous metadata remain BLOCKED. [Tagged resolver configuration](https://raw.githubusercontent.com/moby/moby/v28.0.4/libnetwork/internal/resolvconf/resolvconf.go), [tagged forwarding implementation](https://raw.githubusercontent.com/moby/moby/v28.0.4/libnetwork/resolver.go), [Docker DNS documentation](https://docs.docker.com/engine/network/#dns-services).
3. Capture all IPv4/IPv6 traffic in each selected namespace, plus only the selected bridge. Exact namespace packets are attributable regardless of their claimed IP source. Bridge traffic is attributable when an endpoint is an inspected runtime address; unrelated runner traffic is excluded. No broad private-subnet allowlist is sufficient. Explicit DNS override semantics make the daemon's forwarded questions visible in the selected namespace rather than a host resolver path.
4. Observe random, bounded begin/end internal UDP controls at every selected capture point. Observe a unique synthetic DNS question both to 127.0.0.11 and on the forwarded 127.0.0.1 path in each namespace. Observe bridge controls as well. Empty/listening captures or unlabeled later probes do not pass. Controls must be distinguishable from actual denial probes and workflow traffic.
5. Pin/admit the actual Linux, tcpdump and libpcap build profile. Use immediate delivery and wait until every ending control is printed after the workflow/probes before signaling and reaping the observer. Require complete printed packet counts, zero kernel capture drops and unchanged available per-interface error/drop counters. `ps_recv` is retained diagnostically and is **not equated to printed/captured packets**: Linux may count loopback duplicates that libpcap suppresses. Unknown loss-counter support or unobserved drain remains BLOCKED. [libpcap statistics semantics](https://www.tcpdump.org/manpages/pcap_stats.3pcap.html), [Linux libpcap implementation](https://github.com/the-tcpdump-group/libpcap/blob/master/pcap-linux.c).
6. Reject attributed DNS/TCP/UDP packets outside exact admitted runtime/loopback paths. Require genuine bounded denial probes as separate evidence. Recheck namespace/image/topology/resolver identity across the observed window. Later restart/restore/fault tests change namespaces and do not inherit that packet coverage.

## Proposed ephemeral action for a later bundled approval

This is a proposal, **not authorization or a runnable installation command**. A later request must identify the final reviewed helper source SHA, exact helper artifact SHA256, actual runner/job and supported engine/capture builds before approval.

- Target: one authorized disposable Linux CI runner and only the selected random `gateway-demo-<run>` project. No production/shared Docker host.
- File: a single independently reviewed helper copied to an ephemeral root-owned directory such as `/run/gateway-observer/<run>/capture-helper`, removed when the job ends. No package installation, sudoers, setcap, firewall, Docker daemon, persistent DNS or other security-setting changes.
- Privilege: existing explicitly authorized root invocation solely to open the selected network namespaces and read-only AF_PACKET capture handles. Namespace entry requires the existing applicable privilege; non-promiscuous capture uses existing CAP_NET_RAW. Do not grant capabilities. Drop helper privileges after handles are opened where the reviewed design permits. Tests, browser, database operations, build steps and the main verifier never run under that helper.
- Input: fixed begin/end/stop phases and exact validated state/run/source/image identities. No arbitrary shell, command, environment, destination or filesystem output path. Validate owner-controlled state; reject other projects or widened topology.
- Data: bounded application packet headers, interface loss counters and synthetic control/DNS identifiers. No bearer tokens, credentials, request/result payloads or unrelated runner traffic retained. Prefer a bounded inherited output channel to the ordinary verifier, which writes its own 0600 evidence files, rather than root-owned evidence paths.
- Lifetime: observers must be ready before the business window; bounded buffers/timeouts, explicit ending controls, reap on success/failure/cancellation, and verified cleanup. Exact files, resource identity and privilege use are recorded in a redacted report.

Until a separately approved implementation and genuine runtime evidence satisfy these requirements, the stronger observer gate remains open. Parser fixtures must never be substituted for that execution.
